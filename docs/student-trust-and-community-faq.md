## 1. Why was MyIULMS created, and what problem was it meant to solve?

### 1.1 Simple answer for students

A student found that there was already at least one unofficial IULMS app floating around. That app worked, but it saved the login password on the phone in a form that anyone with basic file access could read back. MyIULMS was started as a rebuild of that idea — same data, same portal, but with the password actually encrypted, a modern interface, and clearer handling of session timeouts.

It was never started as a company product, and it was never started to replace IULMS.

### 1.2 Technical detail

The project-history PDF establishes the origin directly:

- The maintainer obtained an existing unofficial IULMS app (package `com.freaky.iulms`) and inspected it. It was a Kotlin app using OkHttp, scraping `iulms.edu.pk` with `IULmsAuth`, `SimpleCookieJar`, and `HtmlParserUtils`, and it stored saved-account passwords **Base64-encoded in `SharedPreferences`** — a reversible encoding, not encryption. (Recorded in the internal development notes.)
- That analysis is exactly the reasoning behind the current implementation. `Iulms.kt:19` pins the portal host directly; `Iulms.kt:170-186` implements login, `Iulms.kt:114-139` replaces the cookie jar, and `Iulms.kt:567-609` (`SecureStore`) uses `EncryptedSharedPreferences` instead of Base64.
- The PDF also records that a **WebView is not used for login or data fetching** — only for voucher rendering. That remains true today (§6.4).

The PDF covers the earliest phase of the project. Everything after it was verified against the repository instead.

### 1.3 Limits / unknowns

- The PDF is a partial, auto-extracted conversation log. It covers the origin and early design, not later releases, decisions, or distribution. It is treated as historical context only.
- The maintainer's private reasoning after that phase is not something this document can verify.

## 2. If IULMS already has schedules, attendance, results, transcripts and vouchers, why use this app?

### 2.1 Simple answer for students

Because on a phone, using the portal usually means: open a browser, log in, dismiss pop-ups, navigate through menus, find the right page. This app opens straight to your schedule and puts the other sections one tap away, so checking takes seconds instead of a minute of clicking.

Some students will still prefer the portal. That is a reasonable choice and the app is not trying to change it.

### 2.2 Technical detail

The app is a **thin client over the same portal pages**. `MainViewModel.kt` fetches these exact portal endpoints:

| Screen | Portal path |
|---|---|
| Schedule / exam schedule | `/sic/Schedule.php`, `/sic/examschedule.php` (`MainViewModel.kt:270-277`) |
| Attendance | `/sic/StudentAttendance.php` (`MainViewModel.kt:280-282`) |
| Result | `/sic/examresult.php` (`MainViewModel.kt:264-268`) |
| Transcript | `SICDataService.php` with `action=GetTranscript` (`Iulms.kt:209-220`) |
| Vouchers | `/sic/Vouchers.php` (`VoucherDownload.kt`) |

The contribution is navigation and presentation, not new data. The app opens on tab `0` (schedule) by default — `MainActivity.kt:453` `var tab by remember { mutableIntStateOf(0) }` — and `MainActivity.kt:492-494` loads schedules when that tab is shown.

### 2.3 Limits / unknowns

- There is **no measurement** of how much time the app actually saves. Any time-saving figure is an estimate, not a verified result.
- The portal covers strictly more than the app does. The app can never be more current than the portal.

## 4. Is MyIULMS official, affiliated, or a replacement for IULMS?

### 4.1 Simple answer for students

No to all three. It is one student's personal, open-source project. It is not built, approved, reviewed, or monitored by Iqra University. It is not a replacement — it shows less than the portal does, and it will always lag behind it.

### 4.2 Technical detail

`README.md:219` states: *"MyIULMS is an unofficial student project, not affiliated with Iqra University… The app depends on the university portal and may be affected by changes to it."* The licence is MIT (`README.md:221`).

There is no university domain, email, or certificate anywhere in the app. Verified: a grep for `https?://` across all Kotlin sources returns exactly five results — `iulms.edu.pk` (`Iulms.kt:19`), `api.github.com` and `github.com` (`UpdateChecker.kt:23,25`), and two read-only link constants for official university pages (`AcademicPolicyData.kt:57-58`).

### 4.3 Limits / unknowns

- MIT licensing of the source does **not** grant any right to use Iqra University's name or marks; `README.md:221` says so explicitly.
- Whether the university would permit a third-party client is **outside anything this repository can answer.** The project history PDF raised this exact question and the maintainer was advised to check the portal's terms of service. That answer is not recorded anywhere verifiable. **Unknown.**

## 5. Where do my registration number and password go?

### 5.1 Simple answer for students — read this part carefully

Your credentials **are transmitted**. They have to be — the app cannot show you your schedule without logging in to the portal.

They are sent **only** to `iulms.edu.pk`, the university's own portal, over HTTPS. This is the same thing that happens when you type them into Chrome. They are **never** sent to the app's developer, to GitHub, or to any third party. The developer has no server and no database, so there is nothing for them to breach.

Earlier public replies said credentials are "never uploaded anywhere." **That sentence was wrong and should not be repeated.** The accurate sentence is: *"transmitted directly to the university portal, exactly as a browser does, and nowhere else."*

### 5.2 Technical detail — the exact credential flow

```
Iulms.kt:171   jar.clear()
Iulms.kt:173   GET  https://iulms.edu.pk/                     (fetch session cookie)
Iulms.kt:175-179 FormBody: username, password, testcookies=1
Iulms.kt:180   POST https://iulms.edu.pk/login/index.php
Iulms.kt:183   success test = response contains "login/logout.php"   (Iulms.kt:168)
Iulms.kt:184   on success, credentials retained in memory for auto-relogin
```

`Iulms.kt:19`: `const val BASE = "https://iulms.edu.pk"` — a compile-time constant. There is no configurable base URL, no redirect to any other host, and no cleartext traffic (no `usesCleartextTraffic` override and no network security config; `AndroidManifest.xml`).

### 5.3 "Remember me" — on and off

| | Remember me **on** | Remember me **off** |
|---|---|---|
| Encrypted on device | Yes — `Iulms.kt:572-578` `EncryptedSharedPreferences` (`iulms_secure`), AES256-GCM master key (`Iulms.kt:569-570`), AES256-SIV key encryption, AES256-GCM value encryption, master key held by **Android Keystore** | **Nothing is written to disk at all** |
| Written by | `MainViewModel.kt:225-228` → `Iulms.kt:581` | `MainViewModel.kt:230` → `Iulms.kt:603` `store.clear()` |
| Excluded from backup | Yes — `res/xml/backup_rules.xml:9` and `res/xml/data_extraction_rules.xml:8,15` exclude `sharedpref/iulms_secure.xml` from both cloud backup and device-to-device transfer | n/a |

**In-memory handling (this is the part most explanations skip).** Even with Remember me off, the running app holds the plaintext credentials in RAM:

- `Iulms.kt:165` — `private var creds: Pair<String, String>?`, populated on every successful login (`Iulms.kt:184`).
- `MainViewModel.kt:132,134` — `savedUser` / `savedPassword` as plain nullable `String`s.
- This exists so the app can silently re-authenticate when the portal session expires, instead of throwing you back to the login screen every hour (`Iulms.kt:193-196`, `Iulms.kt:199-207`).

So "your password never leaves RAM while the app is signed in" is the honest statement. It cannot be avoided in any HTTPS client — the plaintext must exist in memory before the connection is encrypted — but the app could still scope that copy more tightly and drop it sooner than it currently does (§5.5 for today's behaviour, §15.2 for the open recommendation).

### 5.4 Session cookies

`SessionCookieJar` (`Iulms.kt:114-139`) is a `ConcurrentHashMap` **in process memory only**. It is never written to disk, never included in a backup, and is emptied on sign-out (`Iulms.kt:188-191` → `jar.clear()`). Expired cookies are dropped on read (`Iulms.kt:130-131`).

The `iulms_ui` (theme flag) and `myilms_update_check` (a timestamp) SharedPreferences files **are** included in backups, since only `iulms_secure.xml` is excluded. They contain no personal data.

### 5.5 What signing out clears — and what it does not

**Clears:** session cookies (`Iulms.kt:189`), in-memory credentials (`Iulms.kt:190`), and all in-memory academic state — results, schedules, attendance, transcript, vouchers, student name, error messages (`MainViewModel.kt:248-262`).

**Does NOT clear:** the encrypted saved credentials. `MainViewModel.kt` `logout()` contains no call to `store.clear()`. The code comment at `MainViewModel.kt:245-247` states this is deliberate: *"Signing out ends the network session, but remembered credentials remain encrypted on the device. Unchecking Remember me on a successful login removes them."*

So **signing out is not the same as forgetting your password.** Students who want the password gone must log in again with "Remember me" unticked, or uninstall the app.

### 5.6 Does the app have its own server, database, analytics or crash reporting?

**No, on all four.** Verified rather than assumed:

- **Backend:** the only request host is `iulms.edu.pk` (`Iulms.kt:19`).
- **Database:** no Room, no SQLite, no `@Entity`/`@Database`. Academic data lives in Compose state (`MainViewModel.kt`) and dies with the process.
- **Analytics / telemetry / crash reporting:** a grep across all Kotlin sources for `Log.`, `println`, `Timber`, `Analytics`, `Crashlytics`, `Sentry`, `Firebase` returns **zero matches**. No logging framework is even on the dependency list (`app/build.gradle.kts:39-63`).
- **Permissions:** `AndroidManifest.xml:3` — `INTERNET` only. No storage, camera, contacts, location, phone, or IME permission. Voucher PDFs go to `Downloads/MyIULMS` via MediaStore on Android 10+ and to app-private external storage below that (`VoucherDownload.kt:89-126`), so no storage permission is needed on any supported version.

### 5.7 The one non-portal network destination: the update check

The app contacts **GitHub**, and this happens **automatically**, not only when you ask.

- `MainActivity.kt:156-160` — on every successful sign-in, `vm.checkAutomaticUpdate()` runs. There is also a manual "check for updates" action, which calls `checkForUpdates()`.
- `MainViewModel.kt:98-117` — throttled to **once per 6 hours** (`AUTOMATIC_CHECK_COOLDOWN_MS`, `MainViewModel.kt:29`). The cooldown is checked *before* any network request, and the timestamp is written *before* the request via a synchronous `.commit()`, so a crash or a failure cannot produce a retry loop. The throttle is stored in a separate preferences file (`myilms_update_check`, `MainViewModel.kt:26,30`), not in credential storage.
- `UpdateChecker.kt:33-41` — a plain unauthenticated `GET` to `https://api.github.com/repos/Muhammmad-Ashhad-Ansari/MyIULMS/releases/latest` with three headers: `Accept`, `X-GitHub-Api-Version`, and `User-Agent: MyIULMS-Android`.

**What that request sends:** your IP address, and the string `MyIULMS-Android` as a User-Agent. That is all.

**What it does not send:** no credentials, no registration number, no cookies, no grades, no voucher data, no device identifier, no student identifier of any kind. This is provable from the request construction itself — it uses a **separate `OkHttpClient`** (`UpdateChecker.kt:27-31`) with no cookie jar attached, so portal cookies are physically incapable of being sent to GitHub. `UpdateChecker.kt:53-55` additionally validates that the returned release URL belongs to this repository before trusting it.

**Failure behaviour is silent only on the automatic path.** Both entry points share `runUpdateCheck(reportFailure: Boolean)` (`MainViewModel.kt:63`). On failure the automatic path resolves the state to `null` and shows nothing (`MainViewModel.kt:78-88`); the manual path shows "Couldn't check for updates. Check your internet connection and try again." with a Try again button. Any non-2xx response — including HTTP 403 and 429 rate limiting — is treated identically, as a plain `IOException` (`UpdateChecker.kt:43-44`); there is no separate rate-limit message.

**One thing students should know:** silence on failure does not mean silence on success. The automatic check still shows a dialog when it succeeds, offering "Update available" or "You're up to date" (`MainActivity.kt:1022-1085`).

### 5.8 Limits / unknowns

- Whether Iqra University logs or retains credentials beyond ordinary authentication is **outside this codebase.** Unknown.
- `androidx.security:security-crypto:1.1.0` (`app/build.gradle.kts:53`) is **deprecated** by Google. It is not broken, but it is no longer the recommended approach; migrating to direct Android Keystore use would be an improvement. **Recommendation, not a defect.**
- `EncryptionException` paths in `SecureStore` are swallowed (`Iulms.kt:587-589`, `:597`, `:606`) so the app keeps running. This is deliberate resilience, but it means a keystore failure is silent to the user.
- **No `FLAG_SECURE` anywhere.** Verified by grep. Screenshots and the Recents thumbnail can capture the login screen, including the typed password, and any academic screen. **Recommendation, not a verified vulnerability** — it requires another app or physical access.

## 6. What could still go wrong, even with no MyIULMS backend?

"No backend" removes one risk. It does not remove the rest. This section is the honest version.

### 6.1 Simple answer for students

Even though there is no MyIULMS server, four things can still go wrong:

1. **Your phone.** If Remember me is on, your password sits on the device. On a rooted phone, or one with a malicious app installed, that can be read.
2. **The APK you downloaded.** If you got it from a link, a repost, or a group file rather than the official release page, someone could have modified it. Nobody would be able to tell by looking.
3. **The portal.** If IULMS is compromised, or changes, or goes down, the app breaks — and it breaks *while holding your real credentials*.
4. **Screenshots and sharing.** The app does not block screenshots, and the images you share contain your name.

### 6.2 The device

- Plaintext credentials in RAM during a session (§5.3).
- No screenshot blocking (§5.8).
- Encrypted storage protects a lost or backed-up device well. It does **not** protect a rooted device, or one running software that can read app-private files.

### 6.3 The APK and release chain — the most serious finding

**Verified with the official `apksigner` tool:**

```
$ apksigner verify --print-certs -v MyIULMS-v1.0.5.apk
Verifies
Verified using v1 scheme (JAR signing): false
Verified using v2 scheme (APK Signature Scheme v2): true
Verified using v3 scheme (APK Signature Scheme v3): false
Signer #1 certificate DN: C=US, O=Android, CN=Android Debug
Signer #1 certificate SHA-256 digest:
  fc27702dc58fa23597ea983a9227db642b3510b2b29c12c342d24a979d19aaa3
Signer #1 key algorithm: RSA, 2048 bits
```

That certificate is the **maintainer's local Android debug keystore**, confirmed independently with `keytool` — alias `androiddebugkey`, self-signed subject `C=US, O=Android, CN=Android Debug`, RSA 2048, SHA-256 fingerprint identical to the value above. (The exact keystore command is deliberately not reproduced here: it requires the keystore password, and that must never appear in a shared document, a command line, or a shell history.)

The two fingerprints being identical is what lets Android accept a new build as an update to an installed one. AGP's own record agrees (`app/build/intermediates/signing_config_versions/release/.../signing-config-versions.json`): v2 only, no v1, no v3.

**What this means in practice:**

| | Status |
|---|---|
| APK is signed | Yes (v2) |
| Signature proves who built it | **Only weakly** — it shows whoever built it held this particular debug keystore. It does not certify a publisher |
| Signature survives key loss | **Yes, provided the backup is kept.** A verified offline copy on removable media now exists, so continuity no longer depends on a single machine |
| Suitable for wider distribution | **Undesirable but functional.** This is a developer debug key, not a release-grade key. It works for sideloading continuity; a real release key would be better practice |

**Update continuity has since been demonstrated on hardware.** `v1.0.6` was published using this same certificate and installed over `v1.0.5` on a physical Android 12 device with `adb install -r`. It was accepted as an in-place update: the package's install date was preserved, the data directory was unchanged, remembered login state survived, and the app launched without crashing. So students who already have an earlier version can update without losing saved data.

**The signing key has an offline backup.** A copy is kept on removable media, verified by file hash and by certificate fingerprint, and the media is kept disconnected when not in use. This matters because a debug keystore lives in a single user profile and can be lost to an accidental deletion, a reinstall, or a disk failure — and if it were lost, existing installs could no longer be updated in place. The backup location is recorded in the maintainer's local notes; it is deliberately not published here, and neither copy is in Git.

**The build file still has no signing configuration.** `./gradlew :app:signingReport` reports:

```
Variant: release
Config: none
```

`app/build.gradle.kts` contains no `signingConfigs` block, and `git log -S "signingConfig" -- app/build.gradle.kts` returns nothing. That is intentional here: signing stays a separate maintainer step so no password is ever written into source. Anyone with a JDK and the Android SDK can still clone the repository and build it themselves; a clean checkout simply will not produce a *signed release* artifact on its own, so whoever builds it supplies their own signing key or uses a debug build.

This is consistent with `README.md:114` (*"release builds are unsigned by default. Configure a keystore before distributing…"*): the documented build path really does produce an unsigned artifact, and signing happens afterwards.

### 6.4 The portal

- The app scrapes HTML and JSON from pages that have no public API. If IULMS changes a table or a field name, a screen silently stops working. There is no API contract to fall back on.
- The app re-authenticates automatically when a session expires (`Iulms.kt:199-207`), which means it will re-POST the stored password without asking.
- A compromise of the university portal would reach the app directly, because the app authenticates with real student credentials against a system it does not control.

### 6.5 WebView surface

Two WebViews exist: `VoucherDownload.kt:150` and `VoucherPrintActivity.kt:222`. Both render portal-supplied HTML for PDF generation and printing — **not** for login or data fetching. This is a normal use, but a WebView is a broader attack surface than a plain HTTP client, and it is worth knowing it exists.

### 6.6 Sharing and screenshots

- The app sets **no** `FLAG_SECURE`, so any screen can be captured by a screenshot or the Recents thumbnail.
- **Shared images contain the student's name.** `ShareAcademic.kt:231` draws `studentName` onto every exported PNG — result, transcript, and schedule alike. A student who shares a result card publicly is publishing their name alongside their grades. This is worth a warning in-app and should be in the README.

### 6.7 Limits / unknowns

- `app/build.gradle.kts:22-26` disables release optimization (`optimization { enable = false }`), so the shipped APK is **not** obfuscated or minified. Class and method names are readable. This is a size/readability trade-off, not a vulnerability.
- Whether the debug keystore has a backup anywhere is unknown and unverifiable.
- Real-world stability is **unknown**. See §8.

## 7. How can I tell an APK is really from the maintainer?

### 7.1 Simple answer for students

Partly — and the honest advice is still to **build it yourself from the source**.

The APK is signed with an Android debug certificate, which is the kind of signature a developer gets for local testing. It does not identify a publisher in a durable way. The certificate fingerprint **is** now published in the README, so you can at least check *which* certificate signed the file and confirm that a download matches a version you already have. What it still cannot tell you is who is behind the project. The source is public and MIT-licensed, so reading it, or building it, remains the strongest trust answer available.

### 7.2 Technical detail — what is and is not available today

**Available and verifiable:**

```
# The published v1.0.6 asset is byte-identical to the maintainer's build output
local    app/build/outputs/apk/release/MyIULMS-v1.0.6.apk
         sha256: 0c7592ce4eacec87a81edbcd3486993b48f504dbcabe703c35ca256adcb6f7bc
GitHub   release v1.0.6 asset digest (via API)
         sha256: 0c7592ce4eacec87a81edbcd3486993b48f504dbcabe703c35ca256adcb6f7bc
         → MATCH
```

The same SHA-256 is printed in the release notes and in the README's trust section, so it can be checked without using the API. That proves the file you downloaded is the file the maintainer produced. It does **not**, by itself, prove which source commit was built — see §9.4.

The signing certificate is also published, so a student can confirm that an update carries the same certificate as the version they already have:

```
SHA-256: fc27702dc58fa23597ea983a9227db642b3510b2b29c12c342d24a979d19aaa3
```

**Still missing:**

| Missing | Why it matters |
|---|---|
| A dedicated release keystore | The published certificate is a debug key. It is published and stable, but it is not a release-grade identity and it is not backed by any publisher attestation |
| Source commit SHA stated in release notes | There is still no way to tie a binary to reviewed source without a reproducible build |
| CI build workflow, or published reproducible-build verification | **There is no `.github` directory in this repository at all.** Anyone can still clone and build the app from source themselves; what is missing is automated, published evidence that a given binary was produced from a given commit |
| Full `apksigner` verification output in the release notes | The fingerprint is published; the complete verification transcript is not |

> The README previously carried a *"Build passing"* badge using the GitHub Actions logo. No CI configuration exists in this repository, so that badge asserted a check that was never run; it has been removed rather than left to be discovered.

### 7.3 Building it yourself — what that actually proves

```bash
git clone https://github.com/Muhammmad-Ashhad-Ansari/MyIULMS
cd MyIULMS
./gradlew assembleDebug      # or assembleRelease after adding your own signing config
```

Building from a clone verifies **the code you can read produces an app you can run**. It does not verify the *published* APK, and it does not verify that the published APK was built from that code — that requires the checksum and commit evidence in §9.3 and §9.4.

Students are equally welcome to build from source and use the official portal. Both are reasonable.

### 7.4 Limits / unknowns

- A signature check cannot detect a **source** compromise — only a binary one. Open source is the mitigation here, not the signature.
- `apksigner` was available and used for this report. If a student cannot install Android build tools, they cannot perform this check; the SHA-256 method in §7.2 is the only universally available one, and it requires a trusted channel to obtain the expected value from.

## 8. What does "stable" actually mean here?

### 8.1 Simple answer for students

"Stable" is being used as if it settles the question. It does not. There are five separate claims hiding inside that word, and only two of them are currently true.

### 8.2 Technical detail — the five claims, kept separate

| Claim | Verdict | Evidence |
|---|---|---|
| **The code compiles** | **True** | `./gradlew testDebugUnitTest` and `assembleRelease` both completed successfully |
| **The automated tests pass** | **True** | 74 tests, 0 failures, 0 errors, 0 skipped, re-confirmed from the test-results XML |
| **The APK is signed and updates cleanly** | **True** | v2-signed; `v1.0.6` installed over `v1.0.5` on a physical device with data intact (§6.3) |
| **The signature identifies a certified publisher** | **False** | It is a local **debug** certificate (§6.3). It proves the APK is internally consistent and updates from prior versions; it does not certify who published it |
| **The APK matches reviewed source** | **Strongly supported, but see §9.4** | Local artifact hash == published asset hash; no application code changed since the build |
| **The app is stable in daily use** | **Not established** | One successful upgrade test on one device is not a usage record. `app/src/androidTest/` contains only the generated `ExampleInstrumentedTest.kt`. The app collects no crash or failure telemetry automatically, so reliability is not passively measured — students can still report problems voluntarily through GitHub Issues |

**The unit tests cover logic, not the app.** The 74 tests exercise schedule-interval maths, day-index arithmetic, sticky-header highlight selection, HTML/JSON parsing, transcript analytics, and share-image text formatting (`app/src/test/`). None of them touches the network, the UI, the credential store, or a real device.

### 8.3 Limits / unknowns

- No crash data is collected automatically, because the app ships no crash reporting (§5.6). That is a privacy win and a diagnostic loss: nothing reaches the maintainer unless a student chooses to report it. GitHub Issues remain open and are the only channel, so voluntary reports are how reliability problems get seen at all.
- The device test covered **one phone running Android 12**. Other Android versions, manufacturers, and real-world usage are untested.
- GitHub's download counter is a request count, not a user count. It increments on every download event, is not de-duplicated, and says nothing about whether the file was ever installed. It must not be presented as a number of users.
- **Do not describe the app as stable, verified, audited, or certified in public.** The evidence does not support any of those words.

## 9. How does the app depend on iulms.edu.pk?

### 9.1 Simple answer for students

Everything. The app has no content of its own. Every time you open a screen, it asks the portal for that page, right then. Nothing is saved for later, so the app is only as available as the portal is.

### 9.2 Technical detail

| Behaviour | Implementation |
|---|---|
| Fetch strategy | On demand, per screen, per tab switch — `MainActivity.kt:492-494` refreshes when schedule is null |
| Caching | **None.** No database, no HTTP cache configured on the client (`Iulms.kt:158-166` builds `OkHttpClient` with only a cookie jar) |
| Sync | **None.** No background sync, no push, no WorkManager job anywhere in the project |
| Session expiry | Detected by `isLoggedIn()` returning false (`Iulms.kt:168`), then transparent re-login and retry, twice, via `getHtml` (`Iulms.kt:199-207`) |
| Failures | Surfaced as a message in the UI; `screenLoadStates` tracks per-screen loading/error state (`MainViewModel.kt:57`) |
| Update check | The only non-portal request, to GitHub (§5.7) |

So "all data is pulled live from the portal" is **accurate**, but the word *live* is loose — it invites the inference of push updates or background sync, and there are none. The precise version: *"fetched from the portal each time you open a screen; nothing is stored on the phone."*

### 9.3 Signing — current state and what would need to change

**Now in place:** the signing certificate's SHA-256 is published in the README and in the v1.0.6 release notes, and each release note carries the APK's own SHA-256. The signing key also has a verified offline backup, so continuity no longer depends on one machine (§6.3).

**Still recommendations, not current facts:**

1. A dedicated release keystore, referenced from `app/build.gradle.kts` via a gitignored `keystore.properties`, with `signingConfig` assigned to the `release` build type. `signingReport` currently reports `Variant: release / Config: none`, so signing remains a separate manual maintainer step and a clean checkout cannot produce a signed artifact by itself.
2. The source commit SHA published in each release's notes.
3. A GitHub Actions workflow running `assembleRelease` and `testDebugUnitTest`, so anyone can see that the published artifact reproduces.

**Signing-key continuity matters.** Android requires an update to carry the same signing certificate as the installed app. An APK signed with a **different** key cannot update the existing installation in place — the install is rejected, and the user has to uninstall the old copy and install the new one. That is a normal, recoverable situation rather than a dead end, but it has a cost: uninstalling removes the app's private data, so remembered credentials (the `iulms_secure` store), the saved theme choice, and the update-check timestamp are all lost and the student must sign in again. Academic data is not lost — it is re-fetched from the portal — and voucher PDFs previously saved under `Downloads/MyIULMS` live in shared storage and survive. Android's guidance on this is at <https://developer.android.com/studio/publish/app-signing>.

**What that means for the current situation.** The debug key is now the continuity anchor, so it cannot simply be swapped for a "better" release key without forcing every existing user through that uninstall-and-reinstall cycle. That is the reason any migration needs a deliberate plan and an announcement rather than a quiet rotation — not that current users would be locked out permanently.

### 9.4 Provenance — precisely what can be concluded

**Proven:**
- The published `v1.0.6` asset and the maintainer's local `app/build/outputs/apk/release/MyIULMS-v1.0.6.apk` are byte-identical (SHA-256, above).
- `output-metadata.json` records `versionCode 14`, `versionName 1.0.6`, `variantName release` — matching `app/build.gradle.kts:16-17`.
- Tag `v1.0.6` points at the release commit.
- Between `v1.0.5` and `v1.0.6` only `README.md` and `app/build.gradle.kts` changed. **No Kotlin, manifest, or resource file changed**, so `v1.0.6` ships the same application code as `v1.0.5`.

**Not proven:**
- That a binary was produced from a clean checkout of a specific commit. The evidence is strong circumstantial evidence, not a cryptographic link. Proving it would require a reproducible build or a commit SHA recorded at build time.

**Conclusion:** the shipped app code is unchanged across these releases. Updates change the version and the signing continuity, not the application.

### 9.5 Limits / unknowns

- Portal-side behaviour (rate limiting, session policies, HTML changes) is outside this codebase.
- Whether IULMS will ever provide an official API is unknown. If it does, the entire scraping approach would need replacing.

## 10. How do I report a bug without sharing private data?

### 10.1 Simple answer for students

Report it on GitHub Issues and describe **what the screen looked like and what you tapped** — never your registration number, password, session cookie, grades, CGPA, voucher numbers, or your full name. Redact screenshots. If a bug needs real data to reproduce, say so in the issue and ask for a test account rather than posting your own.

### 10.2 Technical detail

- Repository issues: <https://github.com/Muhammmad-Ashhad-Ansari/MyIULMS/issues>
- **Never include:** registration number, password, session cookies, `iulms_secure` contents, grades, CGPA, transcript screenshots, voucher numbers, or voucher PDFs. Voucher PDFs in particular contain your registration number in the document itself.
- **Safe to include:** Android version, phone model, the app version (`README.md` / About), the screen you were on, the exact wording of any error message, and the steps to reproduce.
- **If a screenshot is needed:** blur the header area and any name shown in shared cards. Remember that shared result/transcript/schedule images contain the student's name by design (`ShareAcademic.kt:231`).
- Because there is no crash reporting (§5.6), an issue report is the **only** way a problem reaches the maintainer. That makes clear, well-phrased reports genuinely valuable.

### 10.3 Limits / unknowns

- A bug that only reproduces with real portal data may not be fixable from a public issue without a test account. Unknown whether the university would sanction one.

## 15. Separation of verified facts, recommendations, and unknowns
